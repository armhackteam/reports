## 1. Executive Summary (Резюме для руководства и инженеров)

Подразделение `ArmHack-Team (Cybersecurity Assessment & Defensive Engineering Unit)` провело независимую техническую оценку рисков и аудит архитектуры криптографического доверия в отношении развертывания Национального удостоверяющего центра Российской Федерации (`Russian Trusted Root CA`, управляемого Министерством цифрового развития, связи и массовых коммуникаций РФ) на конечных операционных системах и в преднастроенных клиентских приложениях. В рамках исследования проанализированы системные последствия ручной установки корневого сертификата, не входящего в глобальные программы аудита CA/Browser Forum, в системные хранилища доверия ОС, а также автономные механизмы доверия, встроенные в клиентское ПО (в частности, `Яндекс Браузер` / `com.yandex.browser`).

В соответствии с международными спецификациями инфраструктуры открытых ключей (PKI — RFC 5280, RFC 8446), доверие корневому удостоверяющему центру предоставляет его закрытому ключу глобальные математические полномочия по заверению криптографических сертификатов для любых доменных имен в мире, если иное технически не ограничено расширениями X.509. Включение неограниченного корневого сертификата в системное хранилище доверия операционной системы структурно изменяет границы безопасности протокола Transport Layer Security (TLS) для всех приложений, использующих системные API валидации.

С точки зрения моделирования угроз PKI (RFC 5280), установка управляемого государством корневого сертификата (Root CA) без расширения `NameConstraints` в системное хранилище доверия ОС технически наделяет владельца закрытого ключа — или любой подчиненный удостоверяющий центр в этой иерархии — архитектурной возможностью осуществлять транзитную Man-in-the-Middle (MitM) инспекцию и терминацию TLS-сессий. При отсутствии на стороне клиента жесткой привязки сертификатов (Certificate / SPKI Pinning) пользовательские сессии аутентификации, проходящие через национальные транзитные узлы, лишаются независимых криптографических гарантий сквозной конфиденциальности.

## 2. Threat Modeling & Scope (Моделирование угроз и область анализа)

### 2.1. Границы доверия и системные участники

Модель безопасности протокола Transport Layer Security (TLS 1.2 / TLS 1.3) фундаментально опирается на строго ограниченный и независимо аудируемый набор корневых сертификатов (Trust Anchors), поддерживаемый в операционных системах и браузерных движках.

* **Доверенная сторона (Root Anchor Authority):** Субъект, владеющий закрытым криптографическим ключом корневого и промежуточного сертификатов (`The Ministry of Digital Development and Communications`, `CN = Russian Trusted Root CA`).
* **Транзитные узлы и сетевые посредники (On-Path Entities & Middleboxes):** Автономные системы (AS), магистральные операторы связи и транзитные комплексы глубокой инспекции пакетов (DPI / ТСПУ), расположенные на маршрутах следования трафика.
* **Конечный узел (Client Endpoint):** Системное хранилище доверия хост-ОС (Windows CryptoAPI, Apple Keychain, Linux `/etc/ssl/certs`, Android KeyStore) и автономные хранилища доверия приложений (`com.yandex.browser`).

```text
+-----------------------------------------------------------------------------------------+
|                                    ГРАНИЦА ДОВЕРИЯ                                      |
|                                                                                         |
|  [Клиентский узел]               [Транзитный узел инспекции]          [Целевой сервер]  |
|  (Хранилище ОС / Браузера)       (Ключи промежуточного Sub-CA)        (Origin Service)  |
|         |                                       |                            |          |
|         |==== TLS ClientHello ==================>                            |          |
|         |     (SNI: service.example.com)        |                            |          |
|         |                                       |==== TLS Handshake =========>          |
|         |<=== Синтезированный сертификат =======|                            |          |
|         |     (Подписан Russian Root CA)        |<=== Подлинный сертификат ==|          |
|         |                                       |                            |          |
|         |==== Открытый HTTP-трафик ============> (Анализ транзитных данных)  |          |
|         |                                       |==== Перешифрованный поток >|          |
```

### 2.2. Нормативные отклонения от международных стандартов PKI

Архитектурные параметры исследуемой иерархии сертификатов демонстрируют три структурных отклонения от международных стандартов управления доверием:

1. **Отсутствие расширения X.509 Name Constraints (RFC 5280, раздел 4.2.1.10):** Ни корневой сертификат `russian_trusted_root_ca.cer`, ни промежуточный сертификат `russian_trusted_sub_ca.cer` не содержат критического расширения `NameConstraints`, которое криптографически ограничивало бы выпуск сертификатов исключительно национальными доменными зонами (`.ru`, `.рф`, `.su`). Вследствие этого ключевая пара технически способна генерировать валидные сертификаты для любых глобальных доменов верхнего уровня (`.com`, `.org`, `.net`, `.io`).
2. **Контур аудита CA/Browser Forum Baseline Requirements:** Коммерческие корневые удостоверяющие центры, включенные в глобальные корневые программы (Mozilla NSS, Microsoft, Apple, Chrome Root Program), проходят регулярный независимый аудит WebTrust или ETSI, подтверждающий регламент генерации ключей в HSM и прозрачность выпуска. Исследуемый корневой УЦ функционирует вне контура глобальных программ доверия.
3. **Сегментация инфраструктуры Certificate Transparency (RFC 6962 / RFC 9162):** Несмотря на то, что `Яндекс Браузер` проверяет сертификаты данной иерархии по внутренним/локальным журналам Certificate Transparency (CT), ручная установка корневого сертификата непосредственно в системное хранилище ОС отключает обязательную проверку глобальных журналов CT для системных служб, десктопных клиентов и стандартных браузеров.

### 4.2. Лабораторная верификация транзитной терминации TLS (Proof of Concept)

В изолированной лабораторной среде, моделирующей работу транзитного узла инспекции трафика с промежуточным ключом подписи, цепочка которого восходит к установленному в ОС неограниченному корневому УЦ, соединение проходит следующие этапы:

1. **Перехват инициализации сессии:** Клиент отправляет пакет TLS 1.3 `ClientHello` с заголовком `SNI: service.example.com`.
2. **Динамическая генерация конечного сертификата:** Транзитный узел на лету формирует конечный сертификат X.509 с полем `SAN = DNS:service.example.com`, подписанный промежуточным ключом доверенной иерархии.
3. **Успешная валидация на клиенте:** Поскольку корневой сертификат присутствует в системном хранилище доверия, а SPKI Pinning не используется, системный TLS-стек подтверждает валидность цепочки (`Verify return code: 0 (ok)`).
4. **Доступность данных прикладного уровня:** Транзитный узел терминирует клиентскую TLS-сессию, получая доступ к открытому HTTP/2-потоку перед его повторным шифрованием к целевому серверу:

## 5. Threat Vectors & Structural Consequences (Векторы угроз и архитектурные последствия)

### 5.1. Вектор угрозы 1: Прозрачная транзитная инспекция TLS (общесистемный контур)
* **Уровень риска:** **CRITICAL** (`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:N`)
* **Предусловие:** Установка сертификата `russian_trusted_root_ca.cer` в системное хранилище доверия ОС.
* **Техническое последствие:** Любой транзитный узел или оператор, располагающий выпускающим ключом, подписанным данным корневым УЦ, получает техническую возможность терминировать и инспектировать TLS-сессии к любым внешним ресурсам (не использующим Certificate Pinning) без генерации предупреждений безопасности.

### 5.2. Вектор угрозы 2: Неограниченный выпуск сертификатов для глобальных пространств имен
* **Уровень риска:** **CRITICAL**
* **Предусловие:** Отсутствие расширения X.509 `NameConstraints` в корневом и промежуточном сертификатах.
* **Техническое последствие:** Вместо криптографического ограничения зонами `.ru` / `.рф` на уровне протокола X.509, корневой центр математически валиден для любых международных доменов (`.com`, `.org`, `.net` и др.). В случае компрометации или нецелевого использования промежуточного ключа конечные устройства не имеют криптографического механизма для распознавания подмены сертификата глобального сервиса.

### 5.3. Вектор угрозы 3: Обход системных ограничений через автономное хранилище приложения
* **Уровень риска:** **HIGH**
* **Предусловие:** Использование преднастроенного клиентского ПО (`com.yandex.browser`) со встроенными якорями доверия на чистой операционной системе.
* **Техническое последствие:** Пользователи и организации, поддерживающие чистоту системного хранилища сертификатов ОС, остаются подвержены рискам расширенной границы доверия внутри сессий данного браузера.

## 6. Mitigation & Hardening Recommendations (Рекомендации по защите и укреплению систем)

### 6.1. Меры защиты для конечных пользователей и системных администраторов

1. **Отказ от установки неограниченных корневых сертификатов в основную ОС:**
   * Не устанавливайте конфигурационные профили (`.mobileconfig` на iOS/macOS) и файлы сертификатов в системные хранилища доверия (`certmgr.msc` в Windows, связка ключей `Система` в macOS, `/usr/local/share/ca-certificates` в Linux, хранилище учетных данных в Android) на основных рабочих станциях.
2. **Строгая изоляция среды (виртуализация и контейнеризация):**
   * При операционной необходимости работы с государственными или финансовыми порталами, требующими сертификатов `Russian Trusted Root CA`, изолируйте эту деятельность внутри выделенной виртуальной машины (KVM/QEMU, VirtualBox) или отдельного физического устройства.
   * Не используйте изолированную виртуальную машину для доступа к корпоративной инфраструктуре, международным облачным сервисам и личным коммуникациям.
3. **Регулярный аудит и очистка системных хранилищ доверия:**
   * Проводите регулярную ревизию установленных в системе корневых сертификатов и удаляйте записи с отпечатком SHA-256 `d26d2d0231b7c39f92cc738512ba54103519e4405d68b5bd703e9788ca8ecf31`.
4. **Инкапсуляция сетевого трафика:**
   * Используйте криптографически стойкие туннели с взаимной аутентификацией (например, WireGuard, IPsec), терминирующиеся за пределами неконтролируемых транзитных сегментов сети.

### 6.2. Инженерные рекомендации для разработчиков приложений

1. **Внедрение привязки открытых ключей (SPKI Pinning — OWASP MASVS-NETWORK-2):**
   * Реализуйте строгую проверку хешей открытых ключей Subject Public Key Info (SPKI) в мобильных и десктопных приложениях (через `network_security_config.xml` в Android или `NSPinnedDomains` в iOS), чтобы клиент отвергал сертификаты, выпущенные сторонними корневыми центрами, независимо от состояния системного хранилища ОС.
2. **Публикация DNS CAA и мониторинг Certificate Transparency:**
   * Настройте строгие записи DNS Certification Authority Authorization (`CAA`) с указанием авторизованных глобальных УЦ и осуществляйте непрерывный мониторинг журналов CT.
3. **Криптографическая защита на прикладном уровне:**
   * Для критически важных операций дополняйте транспортное шифрование TLS сквозным шифрованием и подписью полезной нагрузки на прикладном уровне (JWE / JWS или mTLS с выделенной частной PKI).
