## 1. Executive Summary (Резюме для руководства и инженеров)

Подразделение `ArmHack-Team (Cybersecurity Assessment & Defensive Engineering Unit)` провело независимый технический аудит безопасности и оценку криптографической архитектуры клиентской экосистемы Element Messenger (`im.vector.app` и Element X `io.element.android.x`) и базового децентрализованного протокола связи Matrix. В рамках исследования оценены криптографические границы современной библиотеки `vodozemac` на языке Rust (протоколы `Olm` и `Megolm`), проанализировано сохранение метаданных на федеративных домашних серверах (homeservers) и формализована модель угроз репликации направленного ациклического графа событий (DAG).

В отличие от архитектур с однонаправленными очередями без идентификаторов, протокол Matrix функционирует как открытая федеративная сеть репликации состояний. Каждый домашний сервер, чьи пользователи состоят в комнате, хранит криптографически подписанную синхронизированную копию состояния комнаты и истории графа событий (DAG). Несмотря на то, что сквозное шифрование (E2EE) надежно защищает текст сообщений и медиавложения от операторов серверов, сам протокол федерации структурно реплицирует операционные метаданные — включая глобальные идентификаторы пользователей (`MXID`), списки участников комнат, временные метки событий, реестры ключей устройств и доменные имена серверов — между всеми участвующими узлами федерации.

Техническая верификация подтверждает, что Element и Matrix обеспечивают высокий уровень конфиденциальности полезной нагрузки благодаря прошедшей независимый аудит реализации протоколов `Olm` (двойной храповик для чатов 1:1) и `Megolm` (групповой храповик) в библиотеке `vodozemac`, дополненной механизмом кросс-подписи (Cross-Signing) устройств. Однако с точки зрения защиты метаданных децентрализованная репликация DAG, отсутствие выравнивания длины JSON-пакетов и особенности одностороннего продвижения группового ключа `Megolm` требуют строгой настройки клиентских и серверных политик безопасности.

## 2. Threat Modeling & Scope (Моделирование угроз и область анализа)

### 2.1. Системные границы и федеративная репликация графа состояний (DAG)

Протокол Matrix моделирует историю переписки как распределенный направленный ациклический граф (DAG) с согласованностью в конечном счете (Eventual Consistency), синхронизируемый между домашними серверами по HTTPS API федерации:

* **Клиентские узлы (`im.vector.app` / `io.element.android.x`):** Приложения пользователей, управляющие состояниями храповиков `vodozemac`, ключами кросс-подписи и локальными хранилищами `SQLCipher` / `IndexedDB`, взаимодействующие со своим сервером через Matrix Client-Server API и механизм Native Sliding Sync (`MSC4186`).
* **Исходный домашний сервер (`Synapse` / `Dendrite` / `Conduit`):** Авторитетный узел для учетной записи пользователя `MXID` (`@user:domain.tld`), отвечающий за криптографическую подпись исходящих событий DAG, публикацию каталога открытых ключей устройств и хранение зашифрованных медиафайлов (`mxc://`).
* **Удаленные серверы федерации (Remote Federated Homeservers):** Внешние серверы, подключенные к общим комнатам через Matrix Server-to-Server (S-S) Federation API и получающие полные реплики всех событий состояния комнаты и зашифрованных сообщений.

```text
+-----------------------------------------------------------------------------------------+
|                   ТОПОЛОГИЯ ФЕДЕРАТИВНОЙ РЕПЛИКАЦИИ ГРАФА DAG В MATRIX                  |
|                                                                                         |
|  [Клиент Element A] ──(Matrix C-S API / Native Sliding Sync MSC4186)──> [Homeserver 1]  |
|  (vodozemac E2EE)                                                       (Исходный DAG)  |
|                                                                               │         |
|                                                                 (Федерация S-S API/TLS) |
|                                                                               ▼         |
|  [Клиент Element B] <─(Matrix C-S API / Native Sliding Sync MSC4186)─── [Homeserver 2]  |
|  (vodozemac E2EE)                                                       (Реплика DAG)   |
+-----------------------------------------------------------------------------------------+
```

### 2.2. Соответствие криптографическим и протокольным стандартам

1. **Переход от `libolm` к `vodozemac`:** Современные клиенты Element (`io.element.android.x`, Element Web/Desktop) заменили устаревшую Си-библиотеку `libolm` на `vodozemac` — прошедшую аудит реализацию протоколов `Olm` (тройной Диффи-Хеллман `3DH` + Double Ratchet) и `Megolm` на языке Rust.
2. **Нативная синхронизация Sliding Sync (`MSC4186` взамен `MSC3575`):** Для устранения избыточной нагрузки классического эндпоинта `/sync` и отказа от промежуточного прокси-сервера ранней спецификации `MSC3575`, современные развертывания Matrix реализуют упрощенный протокол Native Sliding Sync (`MSC4186`) непосредственно внутри домашнего сервера.
3. **Аутентифицированный доступ к медиафайлам (`MSC3916`):** Начиная со спецификации Matrix v1.11+, неаутентифицированное скачивание файлов по ссылкам `mxc://` заменено аутентифицированными эндпоинтами, что предотвращает произвольный сбор зашифрованных вложений сторонними лицами, хотя участвующие серверы по-прежнему видят размер файлов и время обращения.

## 4. Technical Analysis & Evidence (Технический анализ и доказательная база)

### 4.1. Инспекция криптографического движка (`vodozemac`: `Olm` и `Megolm`)

Анализ криптографического стека `vodozemac` подтверждает двухуровневую архитектуру согласования ключей:

1. **Попарные каналы `Olm` (Устройство — Устройство):**
   * Устанавливают аутентифицированные каналы 1:1 между устройствами пользователей с использованием ключей `Curve25519` (схема `3DH`) и подписей `Ed25519`.
   * Продвигают симметричные ключи через `HKDF-SHA-256` при каждом обмене сообщениями, обеспечивая как прямую секретность (FS), так и восстановление после компрометации (PCS).
2. **Групповые сессии `Megolm` (Шифрование событий комнаты):**
   * Каждое отправляющее устройство инициализирует исходящую сессию `Megolm`, состоящую из 4-компонентного 128-битного состояния (`R_0, R_1, R_2, R_3`), продвигаемого через `HMAC-SHA-256` для генерации ключей шифрования `AES-256-CBC` и аутентификации `HMAC-SHA-256`.
   * Начальный ключ сессии `Megolm` доставляется авторизованным устройствам участников через попарные события `Olm` (`m.room_key`).
   * **Граница ротации:** Поскольку `Megolm` не выполняет обмен Диффи-Хеллмана на каждое групповое сообщение, для восстановления безопасности после компрометации ключа требуется явная смена сессии (при изменении состава участников, отзыве устройства или достижении лимита сообщений/времени).

### 4.2. Структура событий DAG и незашифрованные метаданные конверта

Хотя поле `ciphertext` внутри события `m.room.encrypted` недоступно для чтения домашним серверам, внешний конверт события Matrix передается и хранится в базе данных сервера в открытом виде:

#### Очищенный дамп федеративного события комнаты (лабораторный перехват):
```json
{
  "type": "m.room.encrypted",
  "event_id": "$[REDACTED_EVENT_HASH]",
  "room_id": "![REDACTED_ROOM_ID]:matrix.example.org",
  "sender": "@[REDACTED_USER]:origin.example.com",
  "origin": "origin.example.com",
  "origin_server_ts": 1791936000000,
  "content": {
    "algorithm": "m.megolm.v1.aes-sha2",
    "ciphertext": "[REDACTED_VARIABLE_LENGTH_BASE64_CIPHERTEXT]",
    "device_id": "[REDACTED_DEVICE_ID]",
    "sender_key": "[REDACTED_CURVE25519_KEY]",
    "session_id": "[REDACTED_MEGOLM_SESSION_ID]"
  },
  "hashes": {
    "sha256": "[REDACTED_CONTENT_HASH]"
  },
  "signatures": {
    "origin.example.com": {
      "ed25519:[REDACTED_KEY_ID]": "[REDACTED_HOMESERVER_SIGNATURE]"
    }
  }
}
```

Как видно из структуры события, каждый федеративный сервер, участвующий в комнате, неизменяемо фиксирует:
* Точный `MXID` отправителя (`sender`) и идентификатор его устройства (`device_id`).
* Временную метку с точностью до миллисекунды (`origin_server_ts`).
* Идентификатор активной сессии `Megolm` (`session_id`) и точную длину шифротекста.
* Криптографическую подпись исходного сервера (`signatures`), доказывающую происхождение события с конкретного домена.

### 4.3. Зашифрованное хранилище медиа (`MXC`) и резервное копирование ключей

* **Обработка вложений:** Клиенты шифруют файлы локально по алгоритму `AES-256-CTR` перед загрузкой в репозиторий контента домашнего сервера (`/_matrix/media/v3/upload`). Ключ `AES-256-CTR`, вектор инициализации (`iv`) и хеш `SHA-256` передаются внутри зашифрованного события `Megolm`. При этом домашние серверы видят точный размер файла и IP-адреса клиентов, запрашивающих скачивание по URI `mxc://`.
* **Резервное копирование ключей на сервере (`m.megolm_backup.v1.curve25519-aes-sha2`):** Исторические ключи `Megolm`, сохраняемые на сервере, шифруются на стороне клиента ключом восстановления (Security Key / Passphrase через `PBKDF2-HMAC-SHA-512`) до отправки на сервер.

## 5. Threat Vectors & Structural Consequences (Векторы угроз и архитектурные последствия)

### 5.1. Вектор угрозы 1: Сбор метаданных через недоверенные серверы федерации
* **Уровень риска:** **HIGH** (Для сценариев, требующих анонимности метаданных)
* **Предусловие:** Участие в федеративных комнатах, где присутствуют пользователи со сторонних или крупных публичных серверов (например, `matrix.org` или неизвестных внешних доменов).
* **Техническое последствие:** Поскольку Matrix реплицирует полный граф событий (DAG) на каждый участвующий в комнате сервер, любой узел в комнате получает в реальном времени список всех участников (`MXID`), события входа/выхода, временные метки сообщений и размеры шифротекстов. При этом запросы на удаление (`m.room.redaction`) носят уведомительный характер и не могут криптографически принудить внешний сервер удалить сохраненные логи.

### 5.2. Вектор угрозы 2: Инъекция фальшивого ключа устройства скомпрометированным домашним сервером
* **Уровень риска:** **HIGH** (При отключенной строгой проверке кросс-подписи)
* **Предусловие:** Компрометация базы данных или административного контура домашнего сервера пользователя при условии, что клиенты собеседников разрешают отправку ключей неверифицированным устройствам.
* **Техническое последствие:** Поскольку домашний сервер управляет каталогом ключей устройств пользователя (`/_matrix/client/v3/keys/query`), скомпрометированный сервер технически способен добавить подконтрольное устройство в профиль пользователя. Если у отправителей не включена блокировка неверифицированных сессий, их клиенты могут автоматически передать ключи будущих сессий `Megolm` подставному устройству.

### 5.3. Вектор угрозы 3: Компрометация ключа активной сессии `Megolm` (отсутствие пошагового PCS в группе)
* **Уровень риска:** **MEDIUM**
* **Предусловие:** Извлечение из памяти одного активного входящего ключа сессии `Megolm` (`session_id`).
* **Техническое последствие:** Так как храповик `Megolm` продвигается детерминированно через `HMAC-SHA-256` без подмешивания новой энтропии Диффи-Хеллмана на каждое сообщение, сторона, получившая ключ сессии на шаге $i$, может вычислить все последующие ключи сообщений $i+1, i+2, \dots, n$ в рамках данного `session_id` до момента принудительной ротации сессии отправителем.

### 5.4. Вектор угрозы 4: Корреляция трафика через Push-шлюзы (`Sygnal`) и размер пакетов
* **Уровень риска:** **MEDIUM**
* **Предусловие:** Использование стандартных push-шлюзов (`Sygnal` -> `FCM`/`APNs`) и передача JSON-событий без выравнивания размера.
* **Техническое последствие:** Шлюзы уведомлений фиксируют тайминги пробуждения устройств и идентификаторы комнат, а пассивные наблюдатели сети могут сопоставлять размер передаваемых HTTPS-пакетов.

## 6. Mitigation & Hardening Recommendations (Рекомендации по защите и укреплению систем)

### 6.1. Меры по укреплению безопасности для пользователей и клиентов

1. **Принудительная верификация кросс-подписи и блокировка непроверенных устройств:**
   * Выполняйте интерактивную сверку эмодзи или QR-кодов (`SAS` Cross-Signing) для всех собственных устройств и устройств собеседников.
   * Активируйте в настройках безопасности Element опцию **«Не отправлять зашифрованные сообщения непроверенным сессиям» (Exclude insecure devices)**, чтобы ключи `Megolm` никогда не передавались устройствам без доверенной криптографической подписи пользователя.
2. **Отказ от публичных серверов для конфиденциальных коммуникаций:**
   * Не используйте учетные записи на крупных публичных узлах (таких как `matrix.org`), где метаданные тысяч комнат концентрируются в единой базе данных.
3. **Использование псевдонимных аккаунтов и маршрутизации через Tor (`SOCKS5`):**
   * Маршрутизируйте трафик клиента Element через `Tor` / `Orbot` (`SOCKS5`) или защищенный VPN-туннель, чтобы исключить логирование реального IP-адреса домашним сервером и узлами хранения медиа (`mxc://`).
4. **Минимизация данных в Push-уведомлениях:**
   * Настройте формат push-уведомлений в режим `event_id_only` или используйте `UnifiedPush` с собственным сервером доставки вместо стандартного канала `FCM`/`APNs`.

### 6.2. Инженерные рекомендации для администраторов серверов Matrix

1. **Развертывание изолированных серверов с ограничением федерации:**
   * Для корпоративных коммуникаций развертывайте собственные серверы `Synapse` или `Conduit` с отключенной публичной регистрацией (`enable_registration: false`) и строгим белым списком доменов федерации (`federation_domain_whitelist`) либо полным отключением внешней федерации.
2. **Сокращение интервала ротации ключей `Megolm`:**
   * Настройте параметры шифрования комнат (`m.room.encryption`), уменьшив `rotation_period_msgs` (например, со стандартных `100` до `20–50` сообщений) и `rotation_period_ms` (например, с `7 дней` до `24 часов`) для минимизации окна жизни одного ключа `Megolm`.
3. **Активация аутентифицированных медиа (`MSC3916`) и политик очистки БД:**
   * Включите обязательную аутентификацию для скачивания медиафайлов и настройте автоматическую очистку старых событий DAG и кеша вложений (`retention` политики в `Synapse`).
